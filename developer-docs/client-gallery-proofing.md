# Client shoot proofing and selected-original delivery

## Photographer workflow

Open **Clients → client profile → Sessions**. The client page contains only a compact list of scheduled sessions and their photo counts/status. Open a session, or use its Upload action, to enter `/admin/clients/{clientId}/sessions/{sessionId}`. All uploads, image browsing, batch results, package selection and private delivery links stay on that dedicated page. Scheduled sessions appear before any photos are uploaded; multiple photo collections are grouped under their booking.

For the first upload, enter a collection name and optional description, review the date (defaults to today in the business time zone), and choose photos. Subsequent uploads reuse that session's saved collection and Media folder. A saved processing counter exposes **Images processing** while originals, thumbnail/header/full variants and private watermarked client previews are being prepared. Only then are images attached and marked Ready. Failures show **Needs attention**, and originals already saved to Media remain recoverable. Interrupted processing leases become actionable after 15 minutes rather than displaying an endless spinner. Apply `20261111200000_client_session_processing` with this release. Upload batches remain sequential on the session page; link navigation is blocked while the batch is running.

New sessions create `Clients/{client name}/{session name} MM-DD-YYYY` in Media. Repeat sessions reuse the client's saved folder. Folder references survive renames/moves; colliding client/session names receive a suffix instead of combining unrelated photos. Existing photos are not moved. Apply migration `20261111180000_client_session_folders` before deploying this version.

Without configured photo-selection terms, the private link delivers all images in that scheduled session. For a manual session, open Send → Photo selection settings, set the allowance (prefilled from the booked package snapshot when present), and choose or create a per-unit library service that adds one photo. The add-on is explicitly associated by ID; no service name is reserved. Its live saved price and checkout currency determine new quotes, and an unpublished DIGITAL product provides the normal OrderItem reference. Existing paid-package flows retain their original entitlement checks. Each download rechecks the active access link, matching site/client/booking, non-canceled booking, download controls and private asset. When linking a paid/fulfilled service-package order, explicitly enter the included-photo allowance, extra-photo price and currency. Existing package-selection and payment requirements remain intact. Extra-photo orders cannot grant another package entitlement.

Upload a batch of JPEG/PNG/WebP images to shared Media, or search/browse existing **private** Media visually. Uploads are sequential with per-file results and a stop-after-current control. Each original can be up to 25 MiB and 80 megapixels. The client queue is bounded to 100 files and 250 MiB per batch, uploaded sequentially; each server request accepts exactly one photo. Next action and proxy envelopes are 26 MiB for multipart overhead. Other Media workflows retain the 12 MiB default and the global 25 MiB maximum. RAW formats are not supported. The original bytes are retained. Public or previously public originals must be freshly uploaded through the private workflow: changing metadata cannot revoke old public URLs/caches. Media gallery and purchase references count toward usage and prevent archiving or changing privacy.

Copy the client's private link manually. No email is sent by gallery creation. Public Portfolio curation remains separate and uses public Media; adding a private original to a public gallery remains prohibited. Package-linked shoots release only entitled selections. Direct session delivery releases all photos in that session. Neither workflow adds photos to the public Portfolio.

## Client workflow and controls

`/proofs/{token}` uses a dark, branded image-only gallery with Select/Selected controls, an extra-photo cart summary, and a full-screen arrow/key/swipe viewer. Grid proofs are capped at 320px and previews at 640px on the longest edge, using a versioned WebP cache (quality 50 for both). It displays reduced-resolution WebP proofs with a repeated **burned-in** watermark. Proofs have a distinct private cache, source EXIF is removed, and the source original is not rewritten. Watermarking discourages reuse; it is not an AI-proof or screenshot-proof guarantee.

The client selects photos, sees included/extra counts and the exact overage price, and can remove extras before finalizing. Confirmation creates an immutable snapshot of image IDs, original asset IDs, package name, allowance, price, currency and total. A terms-version check rejects stale displayed prices. A gallery has one finalized selection even across multiple/reissued access links. Repeated same-selection submissions are idempotent; differing submissions conflict. Adding future gallery images never adds them to an existing entitlement.

A zero-total selection releases exactly the selected originals immediately. Extras create a commerce order and use the site's existing connected Stripe/Square/PayPal checkout. A browser success flag, an order marked paid without verified provider evidence, or a payment with the wrong amount/currency does not grant access. The browser returns through a token-free payment-return page and reloads the original private link from same-tab session storage. The private token is not sent to the payment gateway in the return URL.

Every download verifies current site, client, gallery, access status/expiration, gallery/item download controls, unchanged selected asset identity, source privacy, and payment/refund state. S3/R2 original downloads are authorized first and redirect to an exact-key presigned URL valid for 60 seconds; local server storage streams the authorized original. Previously issued short-lived bucket URLs may remain usable until they expire. Next image optimization must not accept protected local or signed remote image URLs because its public cache would outlive these checks.

## Payment and failure policy

- Pending/authorized payments release nothing. Clients can refresh payment status; existing hosted checkout can be reopened.
- Failed/canceled checkout releases nothing. “Resume or renew checkout” re-verifies the saved provider session server-side. Verified open sessions are reused; only verified expired/voided/canceled sessions without funds can create a fresh payment attempt. Selection, pricing and order remain unchanged. Paid/approved/processing or uncertain states never create another charge. A two-minute lease and row locks serialize retries; prior payment attempts remain in the audit trail, and renewal is capped at ten attempts. Interrupted Stripe/PayPal setup replays the same idempotency key only within five hours. An unknown Square setup outcome, exhausted attempts, or unavailable authoritative verification requires merchant reconciliation rather than risking a duplicate charge.
- Pending refund reservations temporarily block delivery and a failed reservation can roll back; they do not permanently revoke access. Any verified partial or full refund of the extra-photo payment revokes future selected-original delivery for that purchase. Revocation is monotonic, including after a delayed duplicate paid event. Files already downloaded cannot be recalled.
- If the underlying purchased package is canceled/refunded, the shoot is unavailable. No new originals are released.
- Changing/revoking an access link or archiving its gallery takes effect on the next authorization check. Link holders are treated as the client; send links only to the intended recipient.
- Exact configured extra prices are charged. This version does not add tax or shipping to photo overages. Confirm applicable tax treatment before enabling paid extras; do not silently reuse physical-product shipping or tax behavior.

## Migration and deployment prerequisites

The additive migration `20261008013000_client_gallery_purchases` creates optional gallery/package terms, verified payment timestamps, immutable purchase/selection tables, verified-refund revocation and snapshot-integrity triggers. Existing rows get no invented allowance, price, ownership, entitlements or payment verification. Legacy private galleries fail closed for original downloads until migrated to a client-owned package selection workflow.

The formerly unchecked `PortfolioGalleryItem.mediaAssetId` reference becomes an FK marked `NOT VALID` to preserve existing dangling strings without rewriting customer data. New writes are constrained. Audit existing references and tenant consistency, repair intentionally, then separately `VALIDATE CONSTRAINT "PortfolioGalleryItem_mediaAssetId_fkey"`. No production database was changed by this implementation.

Before deployment:

1. Back up the database and test the migration against a representative sanitized copy. Snapshot/selection immutability intentionally prevents destructive cascade deletion of finalized financial records.
2. Verify a 20–25 MiB JPEG through the deployed ingress/proxy and observe memory under concurrent users; the cloud fixture does not establish Railway or CDN request ceilings. Confirm private S3/R2 buckets/prefixes cannot be fetched from a public bucket URL or CDN. Application metadata cannot override a public bucket policy. Keep `MEDIA_ASSET_DIR` outside public/static directories.
3. Confirm all three relevant provider paid/refund webhook event types and signatures are configured. Run sandbox checkout, delayed/duplicate webhook, failed/expired session, partial/full refund and token-revocation tests on the intended gateway. Never test with real customer payments.
4. Review pricing/tax treatment and the explicit uncertain-session reconciliation policy above. Decide operational policy before enabling paid overages.
5. Deploy application and schema together, then verify client-profile creation, batches, proof pixels, selections, exact-image download authorization and cache behavior. No push or deployment is included in this local implementation.

Session photo details place Upload and Send in the page header above the gallery. Send opens a tokenized dialog with the recipient, email action, Copy client link, and Preview gallery. Upload contains the Media chooser. Gallery thumbnails omit captions; filenames and folder paths remain in the Media picker. Completed upload batches collapse into a summary; processing and failed batches stay expanded. Email uses the current stored client address, verifies site/client/gallery and active booking scope, and requires all gallery images to be Ready. The confirmation dialog queues a transactional message through the shared Communications outbox; it does not report provider delivery as complete. Repeated requests reuse a UUID idempotency key. The site-scoped `portfolio.session.ready` template is created on first use without overwriting an existing customized template. Suppression and queue failures remain visible in Communications. Gallery URLs use the configured public app origin.

The session workspace is an image-only gallery using Media’s thumbnail treatment, without filename captions. Clicking a tile opens a viewport-sized private viewer with its filename, original Download link, session Send action, previous/next controls, and arrow-key navigation across paginated results. The viewer fetches signed full-size previews and download variants through the existing scoped gallery media action. New uploads receive a safe client-name/session-date filename plus a 12-character unique suffix and their original extension; existing Media assets and files chosen from Media keep their names. The upload bytes and MIME type are preserved.

Reusable service effects live in `ServiceLibraryItem.deliverables`. Users create or edit their own named services with positive increases to photos, locations and outfit changes. Included services apply once; per-unit selected add-ons multiply effects by quantity. Session quotes combine these with base package counts and save the resolved totals, source library IDs and extra effects in the immutable booking snapshot. Zero or omitted increases preserve legacy behavior. Apply migrations `20261112010000_gallery_extra_photo_addon` and `20261112020000_service_deliverable_increases`. New selections recheck add-on scope and current price; changed terms require review. Finalized selections retain their agreed price and release rules.

The proof gallery has a compact sticky brand header and a remaining-photo counter in its fixed footer. The first selection beyond the included allowance opens an explicit per-photo price prompt before adding it. Accepting authorizes subsequent extras in the current selection flow at the same terms; declining leaves the pending photo unselected. A changed terms version requires fresh extra-photo consent. Final checkout confirmation and server-side price validation remain required.

Each proof and full-screen preview uses an explicit Select / checked Selected control. A brief first-visit tip explains selection, larger previews and paid extras. Dismissal is remembered in browser localStorage under a static help-version key; no access token or client data is stored. How to choose reopens the tip. If browser storage is unavailable, dismissal still works for the current visit.

Proof selection images suppress the normal context menu, copy events, native dragging, text selection and Safari touch callouts in both the grid and full-screen viewer. These are casual-saving deterrents, not access controls: mobile and desktop browsers cannot reliably detect or block OS screenshots. Instructions and authorized original-download links remain usable. Burned-in watermarks and reduced-resolution proof derivatives remain required.

Proof previews close when the empty space around the image is tapped; tapping the photo or using swipe/selection controls keeps it open. Native browser history records the Selected filter and preview as gallery layers. Back closes the preview, then returns from Selected to All photos; photo-to-photo navigation replaces the current preview entry, and explicit close/All actions consume their history layer. Forward restores a gallery layer. The ordinary browser Back behavior resumes on All photos.

The session photo header stays on one row and truncates the session title with its full name available as a tooltip. Touch layouts use labelled icon-only Upload/Send controls when space is tight. It omits the status pill; Send remains disabled until images are Ready. Shared photo skeletons cover initial gallery loading and active processing. A fixed bottom notice says “Client Images Processing” with completed-file progress for the current upload batch; reopened processing sessions use an indeterminate bar because the server does not expose a batch total. Failed processing leaves an actionable alert instead of an endless skeleton.
